# 服务准入、执行身份与生命周期

前置：[HTTP](03_http.md)、[异步](02_async.md)、[契约](01_contracts.md)。目标：解释服务容量和任务所有权，并识别执行中去重与持久化幂等的差别。改编自 [MVP 服务专题及准入示例](SOURCES.md)。

## 分层以后如何传播错误

```text
调用方 → HTTP 路由 → Service → 工作流 → 模型客户端
```

路由处理请求校验和响应表达；Service 处理准入、活动任务与生命周期；工作流处理顺序、状态与业务约束；客户端处理依赖通信。供应商失败时，客户端给出依赖错误，工作流附上阶段与部分结果，Service 结束本次拥有的任务，路由映射公开结果。

这个分工让纯工作流测试无需导入 Web 框架。请求 schema 也不能替代模型回答的业务校验，公开响应不应直接序列化包含内部异常和配置的整个运行对象。

异步服务可以等待某个 POST 完成后再返回；它并不必然采用202、任务队列和轮询接口。每种对外协议都要自己声明并测试。

## 名额、重复请求和排队

在 MVP 的单事件循环策略里，准入依次判断：正在关闭、标识重复、容量已满；全部通过后登记本次标识。拒绝时不调用依赖，也不释放别人的名额。这里容量满立即拒绝；另一种批处理入口可以选择有界排队，两者是不同政策。

同一事件循环中的检查与登记如果没有 await，其他协程不会在该同步片段中间协作切入。这个前提不保证线程安全、多进程一致性或跨机器容量，不能直接扩展为多个 Web worker 的全局控制。

## 运行与追踪示例

运行 [admission.py](../../support/mvp_examples/admission.py)，按 Admission、run_one、main 阅读：

```bash
python support/mvp_examples/admission.py
```

观察两份工作占满名额时，重复 R1 被拒为409，新的 R3 被拒为429，两个拒绝都没有增加依赖调用。取消 R1 并等待它退出后，R3 可以进入。R2 继续独立完成，名额最终归还。

准入登记成功后，run_one 才拥有对应名额并进入需要收尾的范围。未登记成功的调用不能在 finally 中删除标识，否则可能影响真正正在运行的请求。若在其他地方预先登记，任务在首次运行前就被取消也需要独立考虑；这个示例不证明所有调度变体都安全。

## 活动标识并不保存历史结果

示例让 R1 完成后再次提交，实际依赖调用会再执行。活动集合只能防止执行窗口重叠，结束后即清除，也不会跨进程保存。

假设服务已经产生结果，响应在途中丢失：客户端重试相同标识仍可能再次执行、再次收费。持久化幂等还需要操作身份、请求一致性和结果恢复的契约，以及存储和并发约束。不能仅凭一个409分支证明幂等。

MVP 的 request_id 是调用方标识，不是已认证用户身份。知识库 P2 必须独立加入身份认证、所有权与检索／缓存隔离；复用这些示例不会自动得到权限控制。

## 关闭顺序是可验证行为

共享资源的拥有方先停止准入，让已经创建的任务结束或取消，并等待它们退出，最后关闭共享客户端。先关客户端再等任务，可能让仍在使用它的工作发生额外失败。

示例最后断言所有任务结束、活动标识为空且资源已关闭。这是单循环内的协作清理；强杀进程无法保证 finally 运行。进程重启恢复必须读取持久化状态并另做跨进程测试。

轻量 health 检查只说明服务能处理该检查请求；不代表模型账号、索引或数据库已经可用。知识库项目需分别声明 health 与 readiness 的含义，并在就绪前拒绝业务请求。

## 在 P2 中怎样使用

可以复用准入思路、错误分层、受控依赖与事件探针。字段、容量值和HTTP映射要按知识库契约重新确定。先做 [P2](../../projects/knowledge-assistant/02_service.md) 的API与持久化，再逐步加入版本、权限、并发与容器。

这些示例覆盖本地准入与资源生命周期；数据库、持久化索引、身份认证与容器部署由 [P2](../../projects/knowledge-assistant/02_service.md) 的独立任务继续训练。涉及外部副作用的恢复见 [T3](../transfer/03_recovery.md)，需要自行设计并验证。
