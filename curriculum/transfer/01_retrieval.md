# T1：数据与接口变化后的检索迁移

前置：RAG C1–C4、C6–C7。目标：脱离原来的函数骨架，自行设计输入适配与测试，证明核心机制可复用。本任务无预置实现或自动验收器。

## 新需求

输入改为 UTF-8 JSONL，每行对象包含 `document_id`、`version`、`source`、`text`。ID／source 为非空单行字符串，version 为正整数且不能是 bool；同一批次 `(document_id, version)` 不可重复。空行忽略，空白正文不建块；任意一条记录非法时整批导入失败，并报告物理行号。

source 不再是唯一文档标识。不同 ID 可有相同 source，不同版本可有相同正文；检索与引用必须保留 ID、版本、来源、原文区间，不能静默覆盖。区间仍按原始 text 的 Python 字符索引，必须能回到该版本原文。

保持原核心练习契约不变，自行定义新数据结构和适配边界。保留原 Markdown 入口，通过一套项目级检索接口处理两种输入；不要求逐个重写检索算法。搜索结果排序与过滤规则须先写入你的项目契约。

## 公开行为示例

同一 source 下 `document_id="a", version=1, text="甲\n乙"` 与 `document_id="b", version=1, text="甲\n乙"` 都应被保留；任一引用区间 `[0,1)` 必须分别还原到对应文档的 `甲`。相同 ID 不同版本均可导入；完全相同的 ID／版本再次出现应使本批失败。

## 交付与评审

- 提交你设计的入口、数据契约、运行命令与测试；不用既定骨架。
- 覆盖中文、CRLF、空行导致的物理行号、正文重复、source 重复、非法 JSON、布尔版本和批次末尾失败。
- 在相同文本、切分参数和检索语义下，原 Markdown 与新入口的证据正文、原文区间和相关文档结果应可对照；显式解释 ID 映射。
- 说明新适配为何不会让 source 变成伪主键，以及新增元数据对时间／空间的影响。

后续复查再加入一种字段变化，由你先公布兼容策略再实现；不要修改已有测试的期望来隐藏行为退化。转入 [P2](../../projects/knowledge-assistant/02_service.md)时复用这些证据。
