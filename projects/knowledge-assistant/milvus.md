# Milvus 接入：从手写索引到持久化检索服务

Milvus 是知识库项目的向量存储主线。本任务属于 [P2 服务阶段](02_service.md)，前置为 RAG C1–C4、C6–C7 和 [P1 基线](01_baseline.md)。先完成手写索引与评估，再替换存储；本页提供独立任务规格、公开数据与验收矩阵，不提供接入实现或预置自动测试。

## 1. 部署与依赖边界

项目使用 **Milvus Standalone** 作为独立服务，先在本机或 WSL／Docker 环境完成验证。Lite 可用于前期体验，其结果不代替 Standalone 的连接、持久化和重启验收；分布式集群留作规模需求出现后的专题。

在独立项目环境安装 PyMilvus，固定服务器镜像标签／摘要、SDK 和 Python 版本，记录启动配置、持久化目录、连接与关闭方式。课程根依赖仍只服务组件练习，手写 core 不导入 PyMilvus。这里尚无经过实际运行验证的 Milvus 版本组合，实施时对照所选版本的官方文档并保留兼容性证据。

先看[官方快速开始](https://milvus.io/docs/quickstart.md)，再按[Standalone 安装说明](https://milvus.io/docs/install_standalone-docker-compose.md)准备服务。接口调用以所选 SDK 版本为准，不混用不同版本示例。课程不要求开通云服务或购买模型 API。

## 2. 分三步接入

| 步骤 | 中心问题 | 交付与进入下一步的证据 |
| --- | --- | --- |
| M1 · 检索对照 | 相同向量换成 Milvus 后，结果是否符合相同语义？ | 建 collection、写入与检索；使用 FLAT／COSINE，对照手写精确检索 |
| M2 · 数据生命周期 | 权限、版本、重放和删除怎样保持一致？ | 接入服务端身份、业务数据库与版本状态，完成更新删除和故障测试 |
| M3 · 可运行服务 | 进程或容器重启后能否继续使用？ | 持久化、就绪检查、超时与重连策略、可复现启动及跨进程测试 |

M1 使用固定的非零向量即可，不需要真实 embedding 服务。M2–M3 与 P2 的三次交付结合，不增加一条必须全部重学的框架路线。

FLAT 在这里提供精确检索对照，索引类型与距离度量分别配置；先阅读[官方 FLAT 说明](https://milvus.io/docs/flat.md)，确认使用 COSINE，而不是沿用示例中的其他度量。

## 3. 数据契约

每条向量记录至少能够还原以下信息，字段名和具体 schema 自行设计并公布：

| 内容 | 必须满足的要求 |
| --- | --- |
| 记录主键 | 同一业务记录重放保持稳定；不同身份、文档、版本和块不能互相覆盖 |
| 文档身份与所有者 | 与业务数据库中的身份、归属一致，source 不作为唯一文档标识 |
| 文档版本 | 引用能回到所用版本的原文；不能混合新旧版本的块 |
| chunk_id、source、start、end、text | 往返后保持一致，正文等于对应版本原文的切片 |
| embedding 与模型标识 | 同一检索空间的维度、模型和度量保持一致；更换模型后不能直接混搜旧向量 |

输入向量维度与 collection 配置一致，元素必须有限；本任务的 COSINE 对照数据使用非零向量，k 为正整数。错误维度、非法数值、零范数查询或非法 k 在调用检索前明确拒绝，不能静默截断或补零。这是项目适配层的约定，C3 的零向量计算契约保持独立。

原文、认证身份、版本发布与请求重放状态由应用及业务数据库管理；Milvus 保存向量及检索所需字段。明确哪些字段重复保存、如何核验一致性，不能假设 Milvus 与业务数据库共享一个事务。

## 4. 公开检索场景

先固定下表的二维向量、COSINE 度量和 FLAT 精确检索。A、B 是两个已认证测试身份；当前请求属于 A，query=`[1,0]`，k=2。

| 记录 | 所有者 | 文档与版本状态 | 向量 | 是否可作为本次候选 |
| --- | --- | --- | --- | --- |
| a1 | A | doc-1，当前版本2 | `[1,0]` | 是 |
| a2 | A | doc-1，当前版本2 | `[0.8,0.6]` | 是 |
| a3 | A | doc-1，当前版本2 | `[-1,0]` | 是 |
| b1 | B | doc-2，当前版本1 | `[1,0]` | 否，身份不同 |
| old1 | A | doc-1，已失效版本1 | `[1,0]` | 否，旧版本 |
| deleted1 | A | doc-3，已删除 | `[1,0]` | 否，文档已删除 |

预期返回 a1、a2，顺序一致；对应余弦相似度为1和0.8，浮点比较采用已声明的容差。不要先对全库取2条再在客户端过滤，否则可能漏掉本来合格的候选。

过滤范围来自服务端验证的身份和版本状态。应用应在 Milvus 检索请求中限制候选，返回后继续核验可见性与引用；越权记录不得进入重排或生成。不把客户端传入的 owner 或任意过滤字符串当作可信授权。[Milvus 过滤检索](https://milvus.io/docs/filtered-search.md)

对照时使用相同的 chunks、向量、度量、候选范围和 k，并避开同分样例；分开记录 SDK 原始分数与适配层约定。暂不加入融合、重排和多查询，先定位存储替换带来的差异。

## 5. 可见性、版本与删除

功能验收显式使用 Strong 一致性并记录实际配置。Milvus 提供多种一致性级别，默认的 Bounded 不应被当作立即可见承诺；按[官方一致性说明](https://milvus.io/docs/consistency.md)验证写入、更新和删除后的读取。Strong 也不提供应用与业务数据库之间的跨系统事务。

延续 P2 的快照与发布规则：新版本未完成写入和可检索验证时，不发布为当前版本；构建失败保留旧可用版本。更新完成后发起的新查询不使用旧块；删除完成后发起的新查询不返回删除文档及其缓存引用。在途请求按已绑定的版本快照处理，说明何时可以清理旧版本。

同一业务请求的重放不得产生重复记录或额外文档版本；相同请求身份搭配不同内容应冲突。自行设计主键、发布和恢复策略，用并发与故障测试证明；不能仅凭调用 upsert 或收到写入响应就宣布满足全部业务幂等与一致性要求。

## 6. 必交验收矩阵

自行编写单独的集成测试入口。受控客户端测试校验参数和错误传播；涉及存储、检索与可见性的行为必须连接实际 Milvus Standalone。每次使用可识别的测试 collection，清理仅针对该次测试资源。

| 场景 | 预期结果 | 证据 |
| --- | --- | --- |
| 固定向量与手写索引对照 | 相同候选下的 Top-k 与引用字段一致 | 实际 FLAT／COSINE 检索及原始结果 |
| a1–deleted1 公开场景 | 仅 a1、a2，顺序正确；其他记录不进入后续模型 | 检索过滤、返回字段及依赖探针 |
| 合法请求但无候选 | 返回空结果，问答明确拒答，不调用生成 | 实际检索和调用记录 |
| 维度、数值或查询范数非法 | 明确拒绝，不执行检索 | 校验与客户端调用计数 |
| 相同记录与请求重放 | 无意外重复、跨文档覆盖或额外版本 | 主键、查询和业务状态核对 |
| 新版本写入中途失败 | 不发布半成品，旧可用版本仍正确 | 跨组件故障注入及随后检索 |
| 更新或删除完成后的新查询 | 无失效块、旧引用和缓存泄漏 | Strong 下实际读取及快照断言 |
| 关闭并重开应用客户端 | 数据和检索结果保留，资源正确释放 | 实际连接生命周期测试 |
| 停止并重启服务容器，保留数据卷 | 数据仍在，就绪后能查询 | 容器重启与查询脚本 |
| Milvus 不可达或调用超时 | 有限预算、错误可区分、不伪造成功 | 故障注入、错误响应与恢复记录 |

固定 sleep 不代替一致性与就绪条件。没有实际启动 Milvus 或运行容器时，相应项标为未测；课程默认 pytest 与现有 CI 不执行这些项目集成验收。

## 7. 进入性能优化阶段

先交付可复现的精确基线，再按 [P3](03_evaluation.md)需要比较 ANN 索引，例如 HNSW。固定向量、过滤和目标召回率，记录索引／搜索参数、构建时间、内存、写入开销与 p50／p95；近似结果不强制与精确 Top-k 逐条相等。

最终交付包含独立依赖锁文件、Milvus 版本与 schema、主键和身份映射、运行与重启说明、集成测试、对照报告与已知限制。报告按[交付模板](../templates/delivery.md)区分已测和未测行为，不据本机样例声称已验证大规模分布式能力。
