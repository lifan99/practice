# P2：有权限与版本的知识库服务

中心问题：用户能否可靠地导入、更新和查询自己的文档？前置为 P1、基础 F2–F4、迁移 T1 与 T2。项目独立锁定服务与存储依赖；可选 FastAPI 和 SQLite／PostgreSQL，具体版本及兼容性由实际环境验证。

## 分三次交付

先完成文档／问答 API 与持久化，验证一次真实进程重启；再加入两身份隔离、版本竞争与更新删除，完成相应故障测试；最后加入并发／超时预算、取消与容器启动。每次保留一个可运行版本，逐步填写下方矩阵，不要求一次实现整个服务。

## 自行设计服务契约

提供文档创建／读取／更新／删除、问答、健康／就绪检查。HTTP 路径、schema、状态码与同步／异步导入策略由你先公布；至少区分无效请求、未认证、资源不可见、版本冲突、依赖失败与服务忙碌。对已认证用户，越权资源与不存在资源使用相同公开错误行为，列表、统计和其他接口也不能泄露私有文档的存在性。

身份必须由服务端验证的凭据确定。课程可使用两份固定测试凭据映射到两个用户，密钥经环境提供；只适用于本地演示，说明其限制。不能信任请求正文的 owner。所有文档、索引、查询、引用和缓存使用同一身份边界；越权正文不得进入生成或重排调用。日志不记录凭据和原始敏感正文。

文档需要稳定 ID 与递增版本，记录原文、所有者、内容身份和可检索状态。相同请求身份的重放不产生额外版本；不同正文复用同一请求身份明确冲突。更新需要声明期望版本，同时基于同一旧版本的竞争更新至多一个成功。

可同步完成导入，也可返回处理中；**只有可检索版本发布后才算完成**。处理中状态不得把半成品当作当前版本。构建新版本失败时保留原可用版本，不出现新旧块混杂。请求开始时绑定当前可用语料快照，答案携带所用版本；并发更新期间的在途请求可以完成旧快照，但必须按该版本核对证据。

更新完成后开始的新查询只使用新版本；删除完成后开始的新查询不返回该文档、块或旧缓存引用。删除前已开始的请求按已声明快照完成；明确这一一致性边界。数据库与外部向量存储分离时，自行声明失败／恢复策略并证明，不能假定两者共享事务。此阶段允许继续使用精确检索，不要求引入向量数据库。

## 运行与资源约束

持久化原文、版本、身份边界和必要索引信息；结束进程后重新启动仍可查询，可以选择从持久化数据重建派生索引，就绪前明确不可接受查询。使用真实所选数据库进行事务与约束测试；迁移和初始化命令可复现。

为请求大小、并发工作、模型调用、超时与重试公布有限预算；预算值结合硬件自定。展示过载行为，不能无限排队或无限重试。客户端、数据库连接和任务拥有明确生命周期；关闭与调用者取消后完成清理，不把后台子任务遗留给下一次请求。

提供容器镜像和单机启动配置；需要多个服务时可用 [Docker Compose](https://docs.docker.com/compose/intro/features-uses/)。数据持久化位置、配置注入、迁移与健康／就绪语义写入运行说明；本机容器演示不等于验证公网生产部署。

## 公开验收矩阵

| 场景 | 预期行为 | 需要的测试 |
| --- | --- | --- |
| 用户A导入，用户B查询／访问ID | B不能获得A的正文、引用或存在性泄露，符合公开错误策略 | 两身份 API 测试；生成与重排输入探针 |
| 同一请求重放／身份相同正文不同 | 前者结果一致，后者明确冲突 | 持久化统计与返回结果 |
| 两个并发旧版本更新 | 至多一个成功，无混杂索引 | 实际数据库与可控并发测试 |
| 构建新版本中途失败 | 原可用版本可查询，失败版本不可见 | 故障注入与随后查询 |
| 更新或删除完成后的新查询 | 不出现失效块、过期缓存或旧引用 | API 与证据版本断言 |
| 实际结束并重启服务进程 | 数据仍在；索引恢复后就绪，身份隔离保留 | 跨进程启动／查询脚本 |
| 模型超时、请求取消、并发超限 | 失败类别明确、预算生效、资源释放 | 确定性探针与故障测试 |
| 空数据目录首次启动容器 | 按说明初始化成功，依赖异常时不错误标为就绪 | 实际容器运行记录 |

## 交付

交出 API 契约、schema／迁移、项目锁文件、应用测试、容器配置和重现步骤。用真实所选数据库验证权限与数据行为；API 测试可用受控模型避免费用，但另列真实模型兼容性证据。

说明一次事务边界、一个查询索引与一个故障窗口，记录性能与当前限制。评审以矩阵中的行为和证据为准；尚未运行的容器或重启测试须标未测。进入 [P3](03_evaluation.md)前保留一份可重现的 P2 基线版本。
